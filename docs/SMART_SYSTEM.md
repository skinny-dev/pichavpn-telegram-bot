# سیستم هوشمند: حافظهٔ پیام‌ها و انتخاب خودکار سرور

## ۱) حافظهٔ پیام‌ها (برای همهٔ جنبه‌ها)
یک حافظهٔ مشترک برای هر مشتری: چه موضوعی را چند بار، چه وقت و با چه نتیجه‌ای گفته‌ایم. نبض، فالوآپ‌ها و «بهترین سرور» همه از آن می‌خوانند و در آن می‌نویسند (`serverless-bot/tgcloud/lib/memory.js`).

**هر پیام یک «موضوع» و یک «نوع» دارد:** `tip` (آموزش) · `action` (دکمه‌ای که کاری می‌کند: بهترین سرور، تمدید، رأی) · `offer` (پیشنهاد فروش) · `care` (فالوآپ یک‌باره).

| قاعده | رفتار |
|---|---|
| آموزش تکراری | هر موضوع آموزشی **حداکثر ۲ بار** و **نه زودتر از ۳ هفته** |
| لمس‌شده | اگر دکمهٔ یک آموزش را زد، یعنی **یاد گرفته**؛ آن موضوع دیگر نمی‌رود (اکشن‌ها می‌مانند) |
| نادیده | پیامی که ۴۸ ساعت لمس نشود «نادیده» است؛ **۲ بار نادیده و هرگز لمس‌نشده ← آن موضوع ۶۰ روز خاموش** |
| پیشنهاد | ۲ پیشنهاد نادیده ← **۴۵ روز هیچ پیشنهادی**؛ آموزش‌ها ادامه دارند |
| خستگی | ۵ پیام پیاپی نادیده ← نبض **خودکار هفتگی** می‌شود؛ یک لمس خستگی را صفر می‌کند |
| بین سیستم‌ها | اگر نبض دعوت به تست رایگان را فرستاده، فالوآپ C10 همان را تکرار نمی‌کند (موضوع مشترک `test_invite`) |
| تراکنشی | پرداخت، تحویل و «تقصیر ما» هرگز مسدود نمی‌شود |

**آمار برای شما:** `/memory` (ادمین): به‌ازای هر موضوع ارسال، لمس، نادیده و درصد؛ موضوعی با ≥ ۳۰ ارسال و لمس زیر ۳٪ «کم‌اثر» علامت می‌خورد تا بازنویسی یا حذف شود. یعنی سیستم خودش می‌گوید کدام محتوا به درد نمی‌خورد.

**هنوز وصل نشده (فاز بعد):** ارسال انبوه دستی (broadcast)، پست‌های کانال (لمس هر نفر قابل‌ردیابی نیست؛ فقط لینک‌های `start=ch_*`)، و دانستنِ «وصل است و مصرف می‌کند» از پنل برای حذف آموزش اتصال (داده‌اش در پنل هست؛ باید خواند).

## ۲) انتخاب خودکار بهترین سرور
سیستم خودش می‌داند کدام سرور برای چه کاری بهتر است؛ شما چیزی تایپ نمی‌کنید.
1. **فهرست از پنل:** `/api/hosts` پاسگارد هر ۳۰ دقیقه خوانده می‌شود (ریمارک، پورت، نوع امنیت؛ **آدرس‌ها ذخیره نمی‌شود**). از ریمارک تشخیص می‌دهد: `🇮🇷` = تونل، `☁️` = مستقیم، پرچم = کشور خروجی، «✅ ⌛ ∞ 📊» = ردیف اطلاعات (سرور نیست). سرور بدون رمزگذاری (`security=none`) امتیاز منفی می‌گیرد.
2. **آزمون خودکار روی سرور خروجی:** `serverless-bot/tools/probe_exit.sh <کد کشور>` روی هر سرور خروجی (DE, NL, PL, FI, US) هر ۶ ساعت اجرا می‌شود، به Claude، ChatGPT، YouTube، Instagram، Telegram، Google، GitHub و Netflix سر می‌زند و نتیجه (`ok/blocked/down`) را به ریله می‌فرستد (`/probe`). هیچ اطلاعاتی از مشتری خوانده یا ارسال نمی‌شود.
   ```
   0 */6 * * * RELAY_URL=https://pay.theownlypwcha.top RELAY_KEY=<کلید ریله> bash /root/probe_exit.sh FI exit-fi
   ```
3. **نظر کاربران:** بعد از «بهترین سرور برای کارم»، دکمهٔ «✅ جواب داد / ❌ جواب نداد» نتیجه را برای همان سرور و همان کار ثبت می‌کند؛ نظرها امتیاز را بالا یا پایین می‌برد.
4. **امتیاز:** آزمون خودکار (تا ±۵۰) + نظر کاربران (تا ±۴۰) − ۴۰ برای بدون‌رمزگذاری؛ آزمون قدیمی‌تر از ۳ روز نصف می‌شود. سروری که **هیچ داده‌ای ندارد پیشنهاد نمی‌شود** (چیزی ساخته نمی‌شود). اگر داده‌ای نبود، کاربر به پشتیبانی می‌رود؛ متن دستی `/fit` همیشه اولویت دارد.
5. **ادمین:** `/servers` فهرست، آخرین آزمون هر کشور و انتخاب سیستم برای هر کار را نشان می‌دهد؛ `/servers sync` همین لحظه از پنل می‌خواند. CLI: `npx tgcloud run endpoints/admin_servers '{"sync":true}'`.

**محدودیت‌ها که باید بدانید:**
- آزمون از سرور خروجی می‌گوید «آیا آن IP به سرویس می‌رسد»، نه «روی اینترنت مشتری چطور است». کیفیت واقعی روی هر اپراتور را فقط نظر کاربران نشان می‌دهد (اپراتور را هنوز ثبت نمی‌کنیم؛ پیشنهاد فاز بعد: پرسیدن اپراتور با ۴ دکمه).
- تونل و مستقیمِ یک کشور فرض شده همان IP خروجی را دارند؛ اگر نیستند، `probe_exit.sh` را روی هر دو اجرا کنید با برچسب جدا (فعلاً نتیجه به‌ازای کشور است).
- از اینجا (محیط ابری) نمی‌توانم به سرورهای شما وصل شوم؛ پورت‌ها بسته‌اند. تست واقعی روی سرورهای خود شماست.

## ۳) امنیت (مهم)
فهرست کانفیگ‌هایی که فرستادید شامل **UUID** (مشخصهٔ اتصال یک کاربر) و کلیدهای Reality بود و در چت ماند. اگر آن UUID مال یک حساب واقعی (مشتری یا ادمین) است، آن حساب را در پنل «تعویض لینک» (revoke) کنید. آدرس سرورها را هم هرگز در ریپوی عمومی نگذارید؛ این سیستم آدرس‌ها را ذخیره نمی‌کند و از خود پنل می‌خواند.
